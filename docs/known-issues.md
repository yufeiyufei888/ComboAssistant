# 已知问题与路线图

本项目当前是可运行的实验性原型，不是对小米系统级自动连招能力的等价实现。以下问题来自 2026-08-12 的真实游戏试用，优先级高于模拟环境中的自动化测试结果。

## 1. 游戏场景切换后悬浮按键可能消失

现象：在实况足球登录/启动阶段录制的连招，进入开局场景后有时不再显示；在开局内录制的连招，回到启动页面也可能消失。

当前门禁依赖无障碍窗口事件得到的前台包名和屏幕方向。游戏在 Activity、Surface、窗口或场景切换期间产生的事件并不总是稳定，当前实现也没有“同一游戏内多场景”的可靠状态模型。因此即使用户仍认为自己处于同一游戏，连招按钮也可能被隐藏。

后续方向：

- 记录并诊断场景切换期间的包名、Activity、方向和窗口事件序列，但仍不读取窗口文字或内容。
- 为一个连招提供经过用户确认的多场景/多 Activity 绑定策略。
- 增加短暂事件抖动容错和明确的“为何隐藏”状态提示，避免静默消失。

## 2. 悬浮按键缺少位置锁定模式

现象：连招按键一直可以拖动，游戏操作时容易误触并改变位置；现有大小/透明度编辑不足以表达“摆放完成后固定”的状态。

期望交互：

- 编辑模式中调整按键大小、透明度和位置。
- 提供明确的“解锁并拖动”和“锁定位置”开关。
- 锁定后短按只执行连招，不再响应拖动；重新解锁后才能移动。
- 锁定状态与坐标一起持久化，服务或设备重启后保持一致。

## 3. 抬手后逐段镜像阻断连续录制

现象：每次手指抬起后，应用立即进入“正在镜像”状态。在镜像完成前录制层不能继续接收下一次触摸，导致无法自然录制“操作—等待—下一次操作”的完整连续序列。

这是当前“抬手后即时镜像”方案的结构性限制，不只是提示文案问题。普通应用的透明录制层会拦截下层游戏触摸；当前实现选择逐段注入以让游戏跟随，但代价是每段之间出现不可录制窗口。

后续应重新评估录制模型：持续采集所有手势和真实等待时间，直到用户点击“结束录制”后再统一处理/回放；同时明确这种模式下录制过程不会同步操控下层游戏。若仍保留即时镜像，应作为单独模式，并对镜像期间的新输入做排队或给出可预期的状态反馈。

## 已验证但不代表游戏兼容

- Kotlin/JUnit 与 Robolectric/Compose 共 11 项本地测试通过。
- 九张 Compose 截图基线通过，Android 仪器测试源码可编译。
- APK 可以构建并通过签名检查。
- 上述结果不能证明澎湃OS窗口事件稳定，也不能证明具体游戏一定接受无障碍手势。

## 安全与范围

项目不会尝试绕过游戏反作弊，不申请网络、Root、Shizuku 或普通悬浮窗权限，也不采集截图、窗口文字、账号或游戏数据。测试时请使用无账号资产风险的页面，并随时准备使用红色停止按钮终止回放。
