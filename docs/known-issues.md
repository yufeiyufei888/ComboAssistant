# v0.2 Beta 状态与已知边界

v0.2.0-beta.1 在 Redmi K80 Pro 首轮实测中被前台误识别、横屏面板无法关闭和设置球不能移动阻断。v0.2.0-beta.2 修复这些阻断后，Redmi K80 Pro/澎湃OS 已实测确认基本连续录制、保存与回放可用。v0.2.0-beta.3 针对随后记录的三个问题继续改进，但新改动尚未完成 Redmi 实机复验，因此仍保持 Beta；beta.2 的基础功能结论不能替代 beta.3 的专项验收。

## #1 同一游戏场景切换后的悬浮键

Beta 引入独立的前台会话状态机，将同包 Activity/Surface/加载页事件作为会话刷新，将当前输入法、SystemUI、权限窗口等作为临时遮挡；同包事件也会触发差量重算。beta.2 根据实机日志仅在 Accessibility 窗口事件中忽略 `com.miui.screenshot`、`miui.systemui.plugin` 和 `com.miui.systemui.plugin`，真实启动这些包的 Activity 时仍会安全阻断；单条窗口内容杂讯不能自行成为游戏。配置变化后在约 100ms、300ms 复测稳定尺寸和方向。可选的“使用情况访问”首次在本次开机范围内重建 Activity 生命周期状态，随后每秒增量校验。

beta.2 已能进入真实游戏完成基本录制和回放，但游戏内曾偶发显示 `com.miui.securitycenter`。beta.3 将该精确包名归类为临时系统界面：它不能创建、升级或替换游戏会话；出现时先隐藏按键并阻断录制/回放，收到真实游戏事件后恢复。这是保守的 fail-closed 规则，不会把整个包无条件当成可忽略浮层，因为用户也可能真正打开安全中心 Activity。实况足球登录页、加载页、开局与启动页往返，游戏工具箱出现/消失后的自动恢复仍需实机验证。

## #2 悬浮按键位置锁定

beta.2 允许在正常模式直接拖动紫色设置球，松手后持久化位置；拖动不会误触展开，轻点则在展开/收起黑色面板之间切换。连招键在正常模式仍保持锁定，滑动超过阈值只消费，不移动也不执行。设置面板中的“布局按键”会进入一次性工作副本：可拖动当前游戏的连招键，并实时调整选中键的 36–96dp 大小与 20%–100% 透明度。“完成并锁定”统一持久化，“取消”回滚。

黑色面板在横屏限制为约屏幕高度的一半，内容内部滚动，顶部固定“×”关闭按钮；再次点击紫色设置球也能关闭。操作按钮保留至少 48dp 触控区，但可见背景约 36dp 高。布局状态只存在内存中，服务重连后连招键始终恢复锁定。36dp 是连招键视觉直径，触控区域仍至少为 48dp。

beta.3 把红色紧急停止键纳入同一个布局工作副本。用户可拖动它并将视觉直径调整为 36–72dp，默认 40dp，触控区仍至少 48dp；完成时与设置球、连招键一起持久化，取消时一起回滚。布局预览只负责选择和拖动，不会触发停止或连招。

## #3 连续录制与等待

Beta 删除了每次抬手后的即时镜像。录制层持续接收手势，`ACTION_UP` 仅复制轨迹并立即准备下一段；点击“结束并保存”后统一生成时间轴，不自动试播。第一段等待固定为 0，后续等待只记录“上一段抬手到下一段按下”的真实 uptime 差值。

录制期间底层游戏不会响应。普通侧载应用无法用 Android 公开 API 同时完整监听并实时原样透传同一串触摸；依赖游戏画面变化的后续动作只能盲录。小米系统组件拥有普通应用无法获得的输入层能力，因此本项目不能保证 OEM 级等价体验。

点击“结束并保存”时仍未抬起的手势会被丢弃；最后一次抬手到点击结束按钮的尾部等待不会写入连招。这两项是有意的时间轴边界，不属于数据丢失故障。

## beta.3 对三个遗留问题的处理

1. **安全中心误识别：代码已处理，待实机确认。** `com.miui.securitycenter` 只能形成临时遮挡，不能被确认为目标游戏。由于当前没有可靠的实机类名证据区分 Game Turbo 浮层和真实安全中心页面，本版不做宽泛“全部忽略”，以避免在安全中心页面仍向旧游戏坐标注入。
2. **紧急停止按钮布局：代码已实现，待实机确认。** 布局模式可移动并调整 36–72dp 视觉大小；正常回放仍保持至少 48dp 触控区和 fail-closed 挂载门禁。
3. **划掉后台后的服务状态：检测与引导已改善，系统行为仍不可控。** 主界面区分系统开关和实际连接状态，每秒在前台复测，并为澎湃OS提供自启动、省电策略和应用详情的安全入口。普通应用不能自行授予无障碍权限、强制系统重新绑定服务或保证划掉后台后保活；若系统实际关闭授权，仍必须由用户在系统设置中重新开启。

上述三项的 JVM/Compose 自动化结果只证明状态机和界面逻辑；不能证明澎湃OS实际会保活、重新绑定或持续发送足够的前台事件。

## 仍需实机验证

- `com.miui.securitycenter` 出现时是否进入临时遮挡而不被确认为游戏，以及游戏工具箱关闭后能否自动恢复原游戏会话。
- 黑色面板连续展开/收起、横屏滚动和顶部关闭，以及紫色设置球拖动后跨服务重连恢复位置的专项回归。
- 澎湃OS是否持续交付足够的窗口事件，以及 Usage Access 在后台限制下的恢复效果。
- 具体游戏是否接受 `dispatchGesture()`，以及多指/高速轨迹的实际精度。
- Android 对单次 `GestureDescription` 有系统时长上限；0.25× 等低倍速若把某段动作拉长到上限之外，Beta 会拒绝该段而不是冒险注入，需缩短原始手势或提高倍速。
- 红色停止按钮 36dp/72dp、四角位置、旋转和服务重连后的可达性，以及系统取消当前注入时能否在所有场景稳定终止。
- 划掉应用后台后“未启用/等待连接/已连接”状态是否与系统一致，澎湃OS自启动/电池策略入口是否可用；这些入口不代表应用获得保活保证。
- 覆盖安装 v0.1 后旧连招、坐标与 DataStore 设置是否完整保留。

Pull Request 的自动化门禁覆盖代码、模拟环境和固定 API 35 模拟器，API 26 兼容测试按周或手动运行；这些结果均不代表上述实机项目已通过。
